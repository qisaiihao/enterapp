# posts V2 双向兼容部署说明

更新：2026-09-28。当前状态：本地代码与自动测试完成；尚未部署云端，未在真实数据库或新旧安装包上验收。

## 调用量与成本

本次没有新增供客户端调用的云函数，也没有让现有云函数再调用一个“转换云函数”。接口名称、成功返回外壳及旧客户端需要的帖子字段继续保留。

| 操作 | 云函数调用次数变化 | 数据库请求变化 |
| --- | --- | --- |
| 列表、详情、搜索、类型筛选 | 无新增 | 字段转换复用原查询；兼容层不逐帖查询 users，不另查一遍 V1/V2 后拼页 |
| 主发布 contentCheck | 无新增 | 删除发布前的 posts 探测读取，以及插入后的两次颜色/高光补写；同一帖的字段首次 add 写齐 |
| 已读取帖子的编辑/隐藏 | 无新增 | 复用读取时得到的版本，不为兼容额外读取 |
| 未先读取帖子的结构性更新，例如管理员直接改类型 | 无新增 | 首次可能多一次读取，判断该文档适用 V1 还是 V2 PATCH |
| 批量同步昵称、头像、签名等版本相关更新 | 无新增 | 按 V1/V2 分成两次数据库 update；返回合计更新数 |
| 点赞及其他纯计数更新 | 无新增 | 原来的原子更新不变，不因为兼容增加读取 |

转换需要少量计算；新旧查询的 OR 条件可能增加索引扫描成本；旧接口仍返回兼容字段，所以不能按数据库减少的字段比例推算网络流量下降。实际云费用、耗时和索引使用需在测试环境测量。

## 已实现的边界

- [共享模块](../../functions/_shared/posts/index.js)：统一 posts 数据库访问、聚合/lookup 兼容、返回前移除匿名真实身份、事务读写适配。
- [存储契约](../../functions/_shared/posts/schema.js)：创建白名单、V2 精简文档、V2 PATCH 删除空字段与旧别名，以及旧接口视图。
- [查询适配](../../functions/_shared/posts/query.js)：在数据库筛选阶段处理类型字段；聚合在需要投影/计算时补兼容字段，不新增数据库往返。
- [部署目录清单](../../functions/_shared/posts/consumers.json)：45 个目录，包括独立网站 webReader。各目录带 `_lib/posts/`，独立上传可运行。
- [同步与检查脚本](../../scripts/sync-posts-shared.cjs)：共享源码复制到部署目录，并检查副本一致及新增访问者是否进入清单。
- [契约测试](../../scripts/test-posts-schema.cjs)：真实 SDK 查询编码、混合分页、投影、五个创建入口、详情、编辑、匿名权限与发布请求数。
- 前端 `utils/postNormalizer.js` 对旧缓存和新旧字段提供展示回退。

本轮保留各入口原有 V1 查询语义，不顺带重新分类历史矛盾数据；V2 分类统一使用 publishMode。历史文档不迁移，不会因普通编辑自动打上 schemaVersion: 2。

兼容响应只在内存中生成，不能整体回写数据库。V2 创建统一走白名单；V2 更新保留未提交的字段，显式清空则使用删除操作。昵称/头像只存一套；匿名真实作者只供服务端归属、屏蔽与通知使用，不对外返回。

## 写入开关

环境变量：`POSTS_WRITE_SCHEMA`。

| 配置 | 行为 |
| --- | --- |
| 不设置或设置为 `1` | 保持旧格式创建，读取同时支持 V1/V2；适合先部署兼容层 |
| 设置为 `2` | 新增帖子统一使用精简 V2；已有 V2 的编辑仍按 V2 更新 |

该开关仅控制新建格式，不关闭读取兼容。必须在五个创建函数上分别配置：contentCheck、createPost、createDiscussionPost、createSeriesFromSingles、uploadCollagePoetry。调用旧入口的旧 App 也会由服务端按开关生成新格式。

## 部署步骤

1. 执行 `npm run sync:posts`，再执行 `npm run test:posts`。共享源码只能改 `functions/_shared/posts/`，不要手改各函数的生成副本。
2. 对照 consumers.json 部署全部相关云函数及 webReader，确认上传内容包含 `_lib/posts/` 三个文件。第一轮保持写入开关未设置或为 1。
3. 在测试环境准备旧记录及 V2 记录，验证列表、搜索、详情、管理筛选、个人页、活动、作品集、收藏、推荐、周刊、拼贴和网站。
4. 观察包含 schemaVersion / publishMode 的双分支查询计划。按实际过滤及排序建立 V2 组合索引；保留原有 V1 索引。不能仅根据本地测试通过判断云端查询可执行或索引成本合适。
5. 用已发布且拟支持的旧 App、新整包和小程序验证读取及发布、编辑、隐藏/恢复、匿名、删除。旧 App 如曾绕过云函数直读 posts，必须单独识别并处理，不能假设兼容层覆盖它。
6. 全部读取者通过后，将五个创建函数的 `POSTS_WRITE_SCHEMA` 改为 2。抽查各入口新记录有 schemaVersion: 2，没有 isPoem/isDiscussion、重复作者快照等旧字段；检查编辑和资料同步后没有补回来。
7. 再发布整包并观察。由于保留了旧返回协议，不要求为本次数据库精简立即强制更新；具体最低支持版本以旧安装包验收为准。

业务源码未连接生产环境，也没有自动修改环境变量或线上索引。现阶段部署了代码但未设置开关时，仍不会开始精简新写入。

## 回滚

将五个创建函数的开关改回 1，保留已部署的兼容读取代码，已产生的 V2 帖子继续正常读取和编辑。不要退回只认识 isPoem/isDiscussion 存储字段的旧云函数。无需紧急扫描全库补字段。
