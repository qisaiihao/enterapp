# 上传头像后即时刷新个人主页

2026-09-29

## 修复

编辑资料保存成功后，以服务端已确认的新头像地址替换头像专用缓存，同时使个人资料、个人主页摘要和用户资料缓存失效。全局用户资料和本地 `userInfo` 同步更新，持久层保留云文件 ID 或默认头像资源路径，不保存本次选图的临时地址。

头像更新事件携带本次预览地址，已打开的个人主页立即显示新头像，后台继续走现有资料拉取流程取得可访问的云文件地址。保存前已发起的旧资料请求或页面快照不会覆盖新头像；后台读取失败保留当前头像。切换默认头像时清除旧 `avatarFileID`，保存失败或账号已经切换时不写入新头像。

更新发生在资料保存成功后；只选中图片或只上传文件、尚未确认保存，不改变主页头像。没有改变页面布局或新增云函数请求，无需部署云函数。

## 大头像清晰度

后续排查发现，编辑资料的头像选择器强制使用 `sizeType: ['compressed']`，拿到选图结果时细节已经损失。编辑资料与注册页的头像选择入口现统一请求原图，沿用直接上传流程，避免选图阶段的强制压缩。个人主页大头像和点击预览直接使用上传图片的地址，未发现链路中额外追加缩略图处理参数。

`utils/avatarCompress.js` 虽然保留了旧的 200px 压缩逻辑，但当前没有调用方，本次未接入或修改它。已经上传的低清图片不能从缓存恢复丢失的细节，需要重新选择清晰原图上传；新头像继续使用上述即时更新机制。原图文件可能更大，实际清晰度仍受原始照片分辨率影响。

## 保存返回后仍显示旧头像的补充修复

此前测试只覆盖了“保存前发出的请求迟到”。真实页面在编辑页保存后会自动返回个人主页，`onShow` 再次强制拉取资料；保存后新发出的请求若返回旧头像，原有版本判断无法阻止它覆盖新头像。

新增独立的、按用户隔离的五分钟近期保存记录。每次 `getMyInfo` 在缓存或网络读取完成后，以这条已确认保存的头像记录修正返回值及资料缓存，普通清缓存/强刷不会抹掉它；到期后仍保留修正过的资料缓存，避免再次退回旧图，同时不永久阻止其他设备修改头像。云链接按新文件 ID 解析，不增加用户资料查询。主页头像组件按图片地址重新创建，App 原生图片节点不会沿用旧地址对应的节点。

补充的 `scripts/test-avatar-update-h5.cjs` 使用真实路由、编辑页保存逻辑、头像组件和个人主页 `onShow`，仅替换云服务为隔离夹具，不写现网数据。修改前，在保存后返回旧头像的响应场景中复现断言失败；修改后，正常响应和旧头像响应两种场景均确认页面状态、实际 `img.src` 与本地用户资料保持新头像。单元回归同时覆盖保护过期后不退回旧缓存。
