## 已修复的问题

### 1. 批量用户资料接口返回了非公开字段

`functions/getBatchUserProfiles/index.js` 原来直接返回 `users` 集合的查询结果。仓库的注册与登录代码表明该集合包含密码、手机号等信息，因此接口不能返回整条记录。部署前下载的线上代码也确认存在这一问题。

现在数据库查询与响应组装都使用公开字段白名单：`_id`、`_openid`、`nickName`、`avatarUrl`、`bio`。即使数据库适配层意外返回额外字段，响应组装仍会过滤它们。

同时修复批量读取的完整性问题：输入去重并校验，每批最多查询 20 个用户，显式设置数据库返回上限，整个请求最多接受 100 个唯一用户 ID。旧客户端仍收到临时头像 URL；新客户端可传 `rawAvatar: true` 获取原始文件 ID，由统一链接缓存按需换链。新增 `avatarFileID` 字段用于保留云文件身份，不影响旧字段。

### 2. 首页做了没有消费者的头像预取

首页的 `preloadUserData()` 原来额外调用 `getBatchUserProfiles`，将头像放入独立缓存。检查当前页面、组件和 mixin 后确认：页面没有读取这份头像缓存；列表的显示资料来自帖子接口。

删除了这项预取及无用 import。关注状态的预取保留，因为详情页和用户页确实消费它。该改动只涉及首页 script 中的调用，模板与样式保持一致。

### 3. 关注与头像查询重复实现轮询锁，且存在竞态

两个缓存存储原先分别维护加载集合、100ms 轮询和 3/5 秒等待超时。慢请求可能在等待超时后失去锁，引发重复请求；批量查询和单条查询之间也不共享加载任务。旧查询返回后还可能覆盖刚写入的关注状态或头像。

新增 `cache/core/batch-reader.js`，两个存储共同使用：

- 单条、批量及重叠查询按实体复用 `CacheManager.getOrFetch()` 的进行中任务。
- 同一轮缺失实体合并为最多 20 个的批次，控制请求大小。
- 失败或缺失实体不写成成功缓存，下次可以重试。
- 显式更新、清理及账号切换后，旧响应不能重新写入缓存。
- 关注缓存继续按当前账号隔离，TTL 保持一小时；旧公开方法名保留兼容。

头像读取现在保存云文件 ID，并在返回显示结果时统一批量解析链接，避免把临时 URL 当成六小时有效的资料缓存。返回对象与缓存对象分离，链接替换不会丢失文件 ID。用户主页手动写入且仅提供显示 URL 的资料使用 45 分钟缓存。

### 4. 临时图片链接在预热和网络请求期间重复换链

`cache/core/file-url.js` 原先只合并定时窗口内的请求。第一批进入网络阶段后，相同文件再次读取会发起另一批请求；`warm()` 也没有跳过已有有效缓存。

现在每个文件 ID 在整个请求期间共享 Promise，预热复用同一读取路径。保留每批 50 个文件的限制、分批失败保留成功结果、失败重试与过期安全裕量。失效之后的旧响应只能结算原等待者，不能覆盖新缓存或删除新任务。正常运行时只使用统一命名空间保存链接，移除重复的本地缓存副本读取；无缓存管理器时仍保留兼容回退。

### 5. 全量缓存清理后出现新旧命名空间分裂

`CacheManager.clearAll()` 原来清空注册表，但已导入模块仍持有旧 namespace 句柄。后续创建同名 namespace 会产生另一个句柄，第二次清理可能漏掉旧模块的数据或在途请求。

现在清除数据和在途写回资格，同时保留 namespace 句柄身份。关注缓存的全量清理也覆盖尚无持久索引的冷缓存请求。

### 6. 只读用户资料仍查询一份无用帖子

`api-cache/user-profile.js` 的 `getUserInfo()` 现在使用服务端已有的 `onlyProfile: true` 分支，避免为获取资料而额外关联帖子、计算帖子点赞和处理帖子图片。帖子分页仍由原有 `getUserPosts()` 负责。这减少数据库与图片处理工作，不将其算作减少一次云函数调用。

### 7. 缓存目录没有进入质量检查

编码与语法检查原先忽略整个 `cache/` 目录。现已移除该忽略规则，并将缓存目录加入全量语法检查范围。新增回归测试纳入 `npm run test:cloud-savings`，由 `npm run check:quality` 自动执行。

## 可验证的调用收益

| 场景 | 原行为 | 现在 |
| --- | --- | --- |
| 首页获取一批未缓存作者的帖子 | 额外获取一份页面不读取的头像资料 | 该头像云函数请求为 0 |
| 同一轮并发读取 20 个不同实体 | 单条读取路径可能发出 20 次云调用 | 合并为 1 个批量请求 |
| 相同文件在换链进行中再次读取或预热 | 可能再调用一次换链接口 | 共享同一次请求 |
| 对已有有效链接执行预热 | 再次换链 | 无额外请求 |
| 头像链接到期、资料仍有效 | 原缓存可能继续返回旧链接 | 只续期链接，复用资料 |

上表是确定场景与自动测试的结果，不代表整体套餐费用的实测降幅。超过 20 个实体时会分批，以保证完整性；不承诺所有大列表都减少请求次数。此前仓库已经完成的未读轮询、广场气泡与个人帖子缓存优化不计入本轮新增收益。
